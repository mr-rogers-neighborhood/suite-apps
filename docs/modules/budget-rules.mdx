The rules module is two pure steps: evaluate a draft against ranked rules, and
order the rules deterministically. It owns the draft shape, condition matching,
action application and the specificity score. It does not own storage, a
document write, the rule editor or learned-rule creation; those live in the Loro
module and the renderer. Keeping evaluation pure is what lets an import preview,
the Run rules command and a unit test share one implementation.

A rule is a promise that the same inputs produce the same draft. That holds only
if the order is total, so ranking ends in an id tiebreak, and only if matching is
side-effect free, so an invalid regular expression is a non-match rather than a
throw. The draft carries names as well as ids because a person types a name, and
the action writes the id the document stores.

The failure modes are quiet by design. A disabled rule is removed before the
walk; an unknown operator is a non-match and an unknown flag falls back to a null
value; a rule with no
matching condition changes nothing. The outcome is not an error but an unchanged
draft, which the caller can compare against its input.

## legacy/budget/packages/core/src/rules/evaluate.ts#RuleDraft

The draft is the transaction-shaped input to a rule run: ids and names for
account and category, both the display payee and the imported raw payee, plus
date, memo, amount, cleared and flag. It is deliberately not a `Transaction`: an
import row has no id yet, and a test should not need a document. Keeping names
in the draft lets a condition match what a person sees while the action writes
an id.

## legacy/budget/packages/core/src/rules/evaluate.ts#RuleContext

Context supplies the two facts evaluation cannot read from the draft: the
currency and scale used to parse an amount condition, and the id-to-name map
needed to keep `categoryName` in step after `setCategory`. Passing it in keeps
the function pure; the renderer builds it from the same snapshot the draft came
from. A missing category name becomes an empty string, not a failed match.

## legacy/budget/packages/core/src/rules/evaluate.ts#RuleResult

The result is the rewritten draft plus the ids of every rule that matched, in
execution order. It is not a patch or a document: the caller compares the draft
to decide which fields changed, which is what the rules screen does before
writing. Returning all matched ids, not just the last, is what makes "why did
this change" answerable.

## legacy/budget/packages/core/src/rules/rank.ts#specificityScore

Specificity is a number used only for ordering: the strongest operator in the
rule (`is` and `isNot` 5, `oneOf` 4, `notOneOf` 4, `contains` 3,
`doesNotContain` 3, `matches` 2) times ten, plus
the number of conditions. A rule with one exact condition therefore outranks a
broader rule with many loose ones, and a rule with more conditions outranks an
otherwise equal one. The score is not a confidence and is never shown as one.

## legacy/budget/packages/core/src/rules/rank.ts#rankRules

The order is stage first (`pre`, `default`, `post`), then ascending
specificity, then creation time and id. Ascending specificity is the
counter-intuitive part: broad rules run first and the specific rule runs last,
so its action is the one left in the draft. Disabled rules are filtered before
the sort. The id tiebreak makes the order total, so two runs over the same rules
cannot disagree.

## file: legacy/budget/packages/core/src/rules/evaluate.ts

Evaluate owns the matching itself. A condition reads one field; `amount` is
parsed through `money.ts` so a rule compares the integer the transaction stores;
string operators are case-insensitive; `matches` catches an invalid regular
expression and returns false. Actions replace one field, and `setCategory` also
refreshes the cached category name. Nothing here writes, so the same call serves
import, a manual re-run and a test.
