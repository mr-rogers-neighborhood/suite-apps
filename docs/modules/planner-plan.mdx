summary: "The pure projections that turn tasks and settings into a day, a week and a capacity."

The plan module is the arithmetic behind the day, week and capacity views. Every
function takes records and settings and returns plain data: no document, no DOM,
no `fetch` and no timers. `now` is a parameter where a rule needs it. That is
what lets a projection be tested with a hand-built task and rebuilt on every edit
without a cache.

It does not own the records or the write. `scheduledFor` and `order` live on the
task, so moving a task is one document write and every view rebuilds from the
same record. A day record holds an intention, a shutdown note and a capacity
override; it is not a container for the tasks of that day. The views decide how
to draw a `Capacity`; the states are computed here.

## apps/planner/packages/core/src/plan/dayPlan.ts#dayPlan

A day is a partition, not a list. The function walks every task once and sorts it
into planned, completed, overdue or an inbox count. A recurring task is included
only when the date is one of its occurrences, and its done flag comes from
`recurrenceCompletions`; a non-recurring task is included when `scheduledFor`
matches. Overdue is a task scheduled before the date and not done, so a recurring
series is never overdue: its anchor is not a missed occurrence.

Planned tasks sort by `order` then `createdAt`; completed tasks sort by
`completedAt` descending; overdue sorts by the date it was left on.
`plannedMinutes` uses each estimate or the settings default, and
`includeCompleted` can leave the completed list out of a view without changing
the partition. The test pins the four buckets and both recurring cases.

## apps/planner/packages/core/src/plan/capacity.ts#capacityFor

Capacity compares the estimates the day plan already counted with the minutes
the day has. `plannedMinutes` uses the same default estimate, `remainingMinutes`
can go negative, and `ratio` is planned over available; an available zero with
planned work is reported as ratio 2 rather than a division by zero. The state is
derived, never stored: `empty` has no planned work, `comfortable` is below 0.8,
`tight` reaches 0.8, and `over` exceeds the available minutes.

The threshold and the state names are the contract. A view that recomputed a
colour from its own ratio would disagree with the day plan as soon as one
estimate changed. The test pins the empty, default-estimate, tight and over
cases.

## apps/planner/packages/core/src/plan/weekPlan.ts#weekPlan

A week is seven day plans with one start. `startOfWeekKey` resolves the first
date from `weekStartsOn`, then each day is a `dayPlan`; the day's capacity is its
override or the settings default. The week total is the sum of the seven days'
capacities against the open tasks on them, not a stored number.

Carry-over is not a column and not a reschedule. It is
`dayPlan(tasks, today).overdue`, reported with its original dates, so moving one
to today is a separate write. A recurring task cannot be carry-over because
`dayPlan` only reports non-recurring overdue tasks. The test pins both week
starts, a per-day override, and carry-over that stays put.

## apps/planner/packages/core/src/plan/recurrence.ts#occurrencesBetween

A recurrence is projected, never materialised. The task's `scheduledFor` is the
anchor, the rule's `until` caps the range, daily steps by `interval`, weekly
steps by weeks and either the anchor weekday or `weekdays`, and monthly matches
the anchor's day of month. Nothing is written and no occurrence record exists:
completion is a date in `recurrenceCompletions` on the task.

`MAX_OCCURRENCES` caps a projection so a malformed or very old anchor cannot
produce an unbounded list. A monthly rule anchored on the 31st simply has no
occurrence in a shorter month, because the match is on the same day number. The
test pins the anchor, interval, weekday and until cases.

## apps/planner/packages/core/src/plan/recurrence.ts#isOccurrenceDone

Completion of a recurring task is per occurrence. This reads
`recurrenceCompletions` rather than the task's `status`, so completing one
Tuesday does not close the series. `completeTask(id, date)` appends the date and
`uncompleteOccurrence` removes it. The distinction is why `dayPlan` can show a
done occurrence beside tomorrow's pending one, and a view must ask this rather
than check `status`.

## apps/planner/packages/core/src/plan/inbox.ts#inboxTasks

The inbox is a query, not a container. It is every task with no date and status
`inbox`, sorted by priority and then newest first. A null priority sorts last as
9, so an unprioritised capture does not jump ahead of a deliberate `!1`.
Scheduling a task gives it a date and changes its status, which is why it leaves
this list without a delete.

## apps/planner/packages/core/src/plan/search.ts#searchTasks

Search is a fuzzy match over the title plus the project and tag names, so a query
can find a task by a word that is not in its title. The names are passed in
because this module does not join records; the caller supplies the projects and
tags from the same snapshot. An empty query returns an empty list rather than
every task, and the default limit is 25.

The result is tasks, not matches. The score is not exposed, so a view cannot
reorder by it; search stays a filter over records and leaves ranking to the one
library that produced it.

## apps/planner/packages/core/src/plan/reminders.ts#pendingReminders

A reminder is pending only when it has a time, has not fired, belongs to a task
that is not done, and is in the future. Past times are dropped on purpose:
handing one to a platform alarm fires it immediately, and opening the app would
become a burst of old notifications. `now` is a parameter so the rule is testable
without waiting.

The returned schedule is sorted by time and carries only id, title and timestamp.
The scheduler owns delivery and the `remindedAt` write; this function never marks
anything as sent.

## apps/planner/packages/core/src/plan/sort.ts#sortByOrder

`sortByOrder` is the list order for a day or a project: `order`, then
`createdAt` as the tie-break. It returns a sorted copy, so a caller cannot reorder
the snapshot by accident. The same rule is used by `listTasks` and `dayPlan`,
which is why a list, a day and a project agree on what "first" means.

## apps/planner/packages/core/src/plan/sort.ts#nextOrder

The next order is one past the highest order on that date, or 0 when the date has
no tasks. The writer uses this so a new task lands at the end without renumbering;
the document layer's private helper applies the same rule to the tasks it reads
and sends an inbox task to order 0. Neither compacts the existing orders, so gaps
are normal and the sort still agrees.
