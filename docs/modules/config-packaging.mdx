These are build recipes, not a package. Each Flatpak manifest packages the
unpacked tree `package:dir` produced, through `org.electronjs.Electron2.BaseApp`
and zypak, so the sandbox gets Electron's sandbox without a setuid
`chrome-sandbox`. The manifests live beside the wrapper, desktop entry, AppStream
record and icons.

The grants are the product boundary in another form. An app reaches one
documents folder and, where it syncs, the network; the host is the narrow one
because it installs packs into its own data directory and leaves Flatpak
deployments to Flatpak. `scripts/flatpak.mjs` signs the repository summary with
the store key and adds the remote with the public half.

## file: packaging/flatpak/run.suite.desk.yml

The host's sandbox is `--share=ipc`, `--share=network`, Wayland with an X11
fallback, and `--device=dri`. The network namespace carries a pack that declares
the `network` capability; the per-pack session policy and that capability still
decide whether it may reach HTTPS or WSS. There is no host Flatpak service and no
host filesystem grant: the host does not manage deployments, and the document
picker and links go through the portals.

Its desktop entry claims `x-scheme-handler/suite`, so a `suite://` link reaches
the host. A pre-release channel rewrites the manifest id and strips that claim,
so stable remains the one handler.
