The repository-level scripts are not a shipped package. `gate.mjs` builds the
shared libraries and runs each app's gate in dependency order; `release.mjs` holds the release
helpers the publishing paths share — the version, the changelog section, the dirty-tree and gate-proof
refusals; `keys.mjs` reports whether a private key matches its pin; `lib/channel.mjs` and
`lib/keys.mjs` hold the identities and key rules the scripts use; `flatpak.mjs` and
`flatpak-remote.mjs` build and publish the store; `android-release.mjs` publishes Suite Go's APK; and
`release-status.mjs` writes the release bodies and `RELEASES.md`.

A root script has to name its own packages: bare `pnpm -r` would recurse through
every app. The scripts are plain Node with no build step, so the release path is
inspectable without building the thing it releases.

## scripts/release.mjs#gateProblems

The gate proof is a commit, not a working tree. The publish paths share this check: a status file that
did not pass, came from `--only`, came from a warm checkout, or names another commit is refused before
any byte is copied. The relay tarball this module used to build is retired; `sync-v<version>` assets
are history and the relay's last Flatpak ref stays on the signed remote without a new build.

## scripts/lib/channel.mjs#suiteAppId

Stable and pre-release are two identities, and this function names the manifest
one. Stable keeps `<app>`; a pre-release is `slop-<app>` with a hyphen. The
Flatpak id is a different field and keeps its dots (`run.suite.slop.<app>`); the
tier is the branch, so moving from slop to canary replaces the pre-release
rather than adding a third install.

The older dotted `slop.<app>` form is still read for an installed build and is
never written. Keeping that distinction here is what lets the shell, the Flatpak
manifest and the release script agree about which install a card describes.
