A saved view is a shared query and a presentation. `ViewSurface` draws the result
as a table, grid, list or board, or as a graph or chart, and `views/ViewsLayer.tsx`
wraps it in the full-window mode with the rail, the context drawer and the pick.
`views/draft.ts` holds a new view locally until it is created; an existing view is
edited in place through field-level setters.

The module separates three things that are easy to conflate: a view's
configuration is document data, the layer is a mode this reader opens, and a
projection is the view this reader has cast over their own board. Only the first is
shared. `views/availability.ts` is the one switch that decides whether the doors
exist in a build; the code behind them stays. The handbook's views section and
`legacy/canvas/docs/reference/ui.md` own the feature's rules.

## packs/canvas/src/views/availability.ts#viewsEnabled

`false` in every build, not only production. The flag gates the nav-row icon, the
layer, the projection float, the library tab, the two canvas rows that make a view
and the palette rows built from an empty list; the float needed its own guard
because nothing could otherwise project without the layer open.

Shutting the doors is not deleting the feature. A document that already holds saved
views keeps them, and a view card keeps drawing its figure, because a card that
blanks because a feature is paused is worse than a card nobody can edit yet.
Turning the surface back on is this flag plus the mount sites it names; a second
boolean somewhere else is how the two halves would disagree.

## packs/canvas/src/views/ViewSurface.tsx#ViewSurface

Reading and editing are two states of one surface, not two components. In read mode
a cell is a value and a row opens its card; in edit mode the same cell is an input
for the four kinds that edit in place (`text`, `number`, `checkbox`, `select`).
Anything richer shows its value and leaves editing to the inspector, rather than
inventing a text protocol for a relation.

The context and groups are derived from the document at render time:
`resolveContext` answers which cards the view selects, and `groupViewResult`
buckets those same ids, so a grouping never changes what the view finds. Drill-down
is a reading, not a query write: it narrows this reader's surface and shows a
removable chip, because writing it would silently change a shared configuration
when someone opens a bar. A cell write goes through `setProperty` and is therefore
one document edit like any other.
