Start is a package manager with a small UI. It owns the catalogue, the install
records, the channel a card points at, and the launch command. It never reads a
document, never embeds an app, and never proxies document bytes.

It owns what is installed, who placed it, which version and channel it is, and
which process to start for a file or a `suite://` link. It deliberately does
not own an app's files after launch, a Flatpak deployment's contents, or a
document's meaning. A Flatpak is the writer of its own install; Start asks it
and reports the answer.

Two seams carry that split. `PackageBackend` is the one way anything is listed,
installed, updated, removed or launched, so a sandboxed hub swaps transport
without the window learning a second path. `launchPlan` and `launchCommand` are
where routing becomes a separate process, and the renderer only ever sees a
`LauncherState` reported across the preload bridge.

## apps/start/src/catalogue.ts#CATALOGUE_APPS

The catalogue is the list of apps Start can offer, not a list of what it found.
A new machine still gets cards that say what exists and what the feed offers,
which is the one answer a front door cannot leave empty.

Each entry names a contract id, a folder and a feed. It does not name a local
binary; the version and artifact come from the signed feed, and the executable
comes from the install record. The feed URL is repeated here on purpose because
an app that is not installed has no manifest to read it from. Suite Help is the
one entry with no feed: Flatpak installs and updates it, so its card says
`Flatpak` before the store has answered.

## apps/start/src/catalogue.ts#catalogueMatchesContracts

This is the guard that keeps the catalogue honest when a shared contract moves.
It compares the ids, folders and first extensions against `SUITE_APPS`; a
null extension is a fact (Help owns no document), not a mismatch. A failure
names the stale catalogue entry. The fix is the entry, not a looser
check, because the two tables describe the same install to a person and to
discovery.

## apps/start/src/registry.ts#discoverApps

Discovery joins the two records that make one usable app: the manifest an app
ships and the install record Start wrote. It refuses an app with no record, a
record whose executable is not absolute, a manifest that does not parse, a
build that needs a newer contract, and a second copy of an id.

That refusal is the product boundary. A manifest says what an app is; only the
record says what may run, so a tampered manifest cannot point the hub at another
binary. Rejections are returned rather than dropped, which is why a broken
install can still appear as a card.

## apps/start/src/installs.ts#registryAt

`installs.json` is Start's knowledge and the only file that names an executable.
It lives in Start's data directory, never beside a document, and a relative
path is refused on read as well as on write: a record that arrived from
somewhere else is still a path this process would spawn.

The record is written last during an install, so a card may only claim an
install that is complete.

## apps/start/src/packageBackend.ts#PackageBackend

Every package operation crosses this interface: list, install, update, remove,
launch, and the record operations the window needs. The window and the
catalogue consume its data; the native backend is the one module that spawns
`flatpak` or writes a managed AppImage.

The seam exists because a Flatpak-hosted Start has no writable applications root
and no `flatpak` binary. It reaches the host through `flatpak-spawn --host`
behind the same interface, so that grant stays one transport rather than a
second implementation of installing.

## file: apps/start/src/install.ts

The order in this file is the safety property. Nothing enters the install
directory until the download matches the SHA-512 the signed manifest named; the
new version is staged beside the target and moved into place; the record is
written only after the executable and manifest exist.

A failed replace puts the previous version back, and an update keeps exactly one
replaced version for a rollback. An install that fails therefore leaves the
previous install or nothing, never half of both.

## apps/start/src/route.ts#routeLaunch

Routing turns an untrusted target into a plan and refuses rather than guesses.
A deep link is parsed and canonicalised before it becomes an argument; a file
target must be an absolute path with no `..` segment and an extension an
installed app claims.

Nothing here spawns anything. That is why every refusal is a test, and why the
launcher can report "no installed app opens that kind of file" instead of
starting the wrong one.

## apps/start/src/launchCommand.ts#launchCommand

The launch command is data: an executable, arguments and an environment. Keeping
it data is what lets Start stay out of the app's process, and what lets a caller
log or dry-run a launch.

A Flatpak differs only by where its application id sits between `run` and the
opened argument; that belongs to the backend, not to routing. A managed launch
adds one environment variable so the app can tell it was started by the hub.

## file: apps/start/src/launch.ts

The child must outlive the launcher. This file starts the plan through the host
seam, detached and without inherited stdio, then releases it so Start's own
event loop can exit.

The executable comes from a record discovery already checked, and the arguments
from a plan routing already accepted. A launch failure is therefore not a
second place where a path or a link is trusted.
