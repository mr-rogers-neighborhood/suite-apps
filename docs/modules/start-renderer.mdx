The renderer is the hub's window, written as plain DOM modules with no
framework. Everything added here would be a dependency Start carries into a
process whose job is to stay out of the apps, so the page has no bundler and no
import of `@suite/theme` or a UI package.

It owns painting: cards, files, recents, the sync pane, the settings pane, the
rail and the keyboard model around them. It deliberately does not decide whether
an app is installed, whether an update verifies, or what to execute. Main
answers those questions and this directory renders the answer.

The Home Screen is painted here too: one widget shell per resolved placement, with the
app grid's cards inside the `start.apps` one, an app widget's declared capture fields and
settings, and a named placeholder for an id this build cannot resolve. The Screen, the
resolved placements and the fallback note all arrive in `LauncherState`; the rule for those
ids lives in [Widgets and Screens](../reference/decisions.md#widgets-and-screens).

The Screens manager is the host's own surface in the same pane. It lists every Screen and
offers create, rename, duplicate, delete, Set Home and Open; deleting Home asks which Screen
replaces it. The page never edits a document: every action crosses the bridge and returns
the new Screens state, which the page repaints from.

The seam is the preload bridge. `globalThis.suiteStart` exposes `listApps`,
actions and broadcasts; the page treats it as read-only input and re-reads
after every action rather than predicting the result. A boundary test keeps
`child_process`, the Flatpak module and any process spawn out of this directory.

## apps/start/src/renderer/launcher.js#render

One paint from one `LauncherState`. The page stores the last state so a
progress event can redraw the cards alone, then renders every pane from the
same answer.

The theme is already resolved by main and arrives as custom properties, because
this page cannot import the theme package. The rail badge counts only unhealthy
installs and hides at zero, so a healthy hub stays quiet.

## apps/start/src/renderer/launcher.js#applyTheme

Every colour role is a CSS custom property, so the stylesheet never asks which
preset is active. `data-theme` and `data-theme-mode` are set as well, because a
preset can change a border or shadow rule rather than only a colour.

Setting this from state rather than from the control is what makes a choice in
one window correct in the next.

## apps/start/src/renderer/apps.js#renderApps

The apps pane draws the cards the catalogue and discovery produced, in the
order main sent them, with the progress entry and launch error for each id. An
empty list is a state with a message, not a blank region.

A card is not composed here: the state, ownership, actions and refusal copy
arrive in the card. This function chooses placement and redraw, not policy.

## apps/start/src/renderer/rail.js#installRail

The rail is a tab set, so it uses tab roles rather than listbox roles: arrow
keys move and select together, Home and End reach the ends, and only the
selected tab is in the tab order.

Keeping selection and focus in one place is what lets the Cmd/Ctrl+1..4 shortcut
and a pointer click agree on which pane is showing.

## apps/start/src/renderer/home.js#renderHome

The page draws one shell per resolved placement, in the Screen's order, at its size class,
with the title, capture fields, settings and notes main resolved. It never decides which
widget exists or whether an unknown id may be dropped: an unknown placement arrives named
after its registry id with a note, and is drawn like any other.

Edit layout is a mode, not a drag gesture. Every control is a named button or picker, and a
focused placement answers Alt+Left and Alt+Right, so moving is reachable without a pointer.
`renderApps` runs after this and fills the lists inside the app-grid shell, so the cards,
installs and launches are the same code they were before the Screen existed.

## apps/start/src/renderer/screens.js#renderScreens

The manager is Start's, not an app's. It draws the list, each row's roles and the controls
that create, rename, duplicate, delete, set Home and open a Screen. Deleting Home is a
two-step answer: main refuses the first press and returns the other Screens as choices, so
the row asks which one becomes Home before the deletion happens. The last Screen's Delete is
disabled because an empty set has no surface left to create another on.
