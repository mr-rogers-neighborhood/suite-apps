This module is the typed layer over the one Loro document a workspace owns.
`WorkspaceDocument` is the only writer; the domain files behind it (`tasks`,
`projects`, `tags`, `days`, `events`, `focus`, `notes`, `settings`, `meta`) each
own one root and one set of records. Every record read parses through a Zod
schema; the note containers are the exception, because they return Loro maps or
text. Every write touches the keys that changed, then commits once.

It does not own the file, the renderer replica or the projections. Main calls the
same facade and keeps the authoritative instance; the renderer calls it through a
replica and forwards deltas. Only this directory imports `loro-crdt`, which is
what makes "no component constructs a CRDT value" a rule rather than a
convention.

The root names are the storage contract: `tasks`, `projects`, `tags`, `events`,
`days`, `focusSessions`, `settings`, `meta`, and `note:<taskId>` for a note. A new
collection is a root and a domain file, not a field on an existing record.

## apps/planner/packages/core/src/loro/WorkspaceDocument.ts#WorkspaceDocument

The facade is the only writer. Its methods validate through Zod, write leaf keys
rather than a whole record, and commit once per call; the class exposes no raw
map or transaction to a caller. `loro` is the one escape hatch, documented for the
note editor, which binds a ProseMirror view to a container.

One instance is created with `create` or opened with `fromSnapshot`; the
constructor is private, so there is no half-initialised document. `create`
initialises meta and settings before the first read. `workspace.test.ts` pins the
field-level update, the snapshot round trip, both note containers and a
two-replica merge.

## apps/planner/packages/core/src/loro/WorkspaceDocument.ts#WorkspaceDocument.fromSnapshot

Opening is where identity and schema are decided. A fresh peer id is assigned
because reusing the id baked into the snapshot makes the first local edit collide
with the document that produced it. `ensureCurrentSchema` then upgrades an older
document or throws `WorkspaceSchemaError` for a newer one, before any caller can
read a record through this build's schema.

`migratedFrom` is how a host learns that the upgrade was a local commit made
before it subscribed. Without it, an update stream would never carry the upgrade;
the renderer uses it to adopt the snapshot.

## apps/planner/packages/core/src/loro/WorkspaceDocument.ts#WorkspaceDocument.observe

The subscription reports local updates only. A local commit produces bytes, which
the replica forwards to main; an update applied with `applyUpdate` does not echo
back, so a replica cannot forward the same delta twice. That is the property that
makes one `observe` call site enough.

The listener is synchronous and receives raw bytes. It does not know which record
changed; the replica rebuilds a snapshot instead of applying a patch.
Unsubscribing detaches the listener, which is what `DocumentReplica.replace` does
before opening a new document.

## apps/planner/packages/core/src/loro/WorkspaceDocument.ts#WorkspaceDocument.applyUpdate

`applyUpdate` imports a delta from outside this process: main's commit path, or a
synced update. It does not validate or transform the bytes; Loro imports them, and
the next read parses each record through Zod. The trust boundary is therefore the
caller. IPC parses the payload as a binary update, and sync carries the same delta
a local edit produced.

## apps/planner/packages/core/src/loro/WorkspaceDocument.ts#WorkspaceDocument.snapshot

A snapshot is a full document, not a delta. `snapshot()` commits pending
operations first, then exports, which makes it the flush point for a file write
and for boot adoption. `getSnapshot()` is the different read: a parsed
`WorkspaceSnapshot` of records, not bytes.

Confusing the two is the easy mistake. File encoding and adoption need bytes; the
renderer and the projections need records. The names are close on purpose, but
the return types are not interchangeable.

## apps/planner/packages/core/src/loro/WorkspaceDocument.ts#WorkspaceDocument.validate

`validate` parses the whole read model and answers with a `Result` instead of
throwing. It exists for the open path: a candidate file that decodes but contains
a malformed record is skipped in favour of the backup, and an explicit import is
refused instead of replacing a working document. The error is the schema failure,
not a new message, so the log says which record broke.

## apps/planner/packages/core/src/loro/snapshot.ts#readWorkspaceSnapshot

The read model is assembled by parsing every root: tasks, projects, tags, events,
days, focus sessions, settings and meta. A missing record is not a special case; a
malformed one throws at the root that owns it. The replica calls this after every
update, so the cost is one pass over the document rather than a cache that can go
stale.

The shape is plain data. Nothing in it holds a Loro container, which is why a
component can receive it without the ability to write.

## apps/planner/packages/core/src/loro/tasks.ts#createTask

Creation supplies what a draft does not: an id, timestamps, a status and an
order. A task with a date starts `planned` and one without starts `inbox`; the
order is one past the highest in that day, so a new task lands at the end without
renumbering the list. The caller may pass an order, but the default is the
invariant.

The record is parsed before it is written, so an invalid estimate or date fails
here rather than becoming a map with a bad key. The write sets every field of the
new record in one commit.

## apps/planner/packages/core/src/loro/tasks.ts#updateTask

An update merges the patch over the current record, parses the result, and writes
only the keys that were present in the patch plus `updatedAt`. That is why two
replicas editing different fields keep both writes: neither replaces the record.
A patch key set to `undefined` is ignored rather than written, so a form cannot
clear a field by accident; clearing a nullable field is `null`.

A missing task throws `TaskNotFoundError`; an invalid merged record fails the
schema before anything is written. `workspace.test.ts` pins the one-update commit
and the two-replica merge.

## apps/planner/packages/core/src/loro/notes.ts#getNote

A note is not a task field. It is a root keyed `note:<taskId>`, and the key can
hold two container types at once: the rich note is a `LoroMap` tree written by the
editor, and the legacy note is a `LoroText`. Loro separates roots by container
type, so the upgrade sits beside the old value instead of rewriting it.

`getNote` prefers the map once it has a `nodeName` and flattens its children to
words, one line per block; without a map it reads the text. The compatibility is
one-way: an older build reads the text and never sees the rich note. The test
keeps both roots in one snapshot and proves the map wins.

## apps/planner/packages/core/src/loro/meta.ts#ensureCurrentSchema

Migration happens on open and is additive by rule. For a document that already
has settings, this build's upgrade adds the field schema 2 introduced; a document
from an older schema is stamped with the current version. A document from the
future throws `WorkspaceSchemaError` with both versions in the sentence. The
write is committed here, before the renderer subscribes, so every host sees the
same schema.

`migratedFrom` is the return value rather than a second query. A host that needs
to send the upgraded document to another process can tell that an upgrade
happened, instead of watching an update stream that started too late.
