This tour follows a single line of capture from the input that accepts it to the
day that displays it. The line is parsed by a pure function, resolved into real
project and tag ids, written as a task through the one document writer, carried
to the main process as a CRDT delta, and read back by pure projections. The core
package owns the record, the file envelope and the projections; the renderer owns
the form, the replica and the view state. Neither needs a network to do any of
it, and sync is an optional transport over the same deltas.

## apps/planner/src/renderer/src/capture/CaptureBar.tsx#CaptureBar

Capture begins in the renderer because that is where the person is, not because
the renderer owns the task. The component keeps the current input text in React
state and the focus signal in the UI store, then hands the submitted string to
the parser. A day target supplies an implied date; the inbox target does not.

## apps/planner/packages/core/src/capture/parse.ts#parseCapture

The parser is pure: one line in, a draft out. It removes the tokens it
recognises (a day, a clock time, `#project`, `@tag`, `!1`, `~45m`) and leaves
everything it does not recognise in the title rather than dropping it. A time
with no date borrows the implied date, which is why the same line means a
different day in the day view and in the inbox.

## apps/planner/src/renderer/src/capture/resolve.ts#resolveProjectId

A draft names a project by text; the document stores an id. Resolution is a
renderer decision made immediately before the write: an existing name matches
case-insensitively, and an unknown name creates the project through the document
facade. Doing this in the parser would give a pure function a side effect and
would make a parse test depend on a workspace.

## apps/planner/packages/core/src/schema.ts#taskSchema

The draft only becomes a task if it satisfies this schema. Defaults do the work
of making an old document readable: a field added later is absent from older
records and arrives with its default. A field that is not accepted here cannot
survive a read, whatever a writer puts on the map, which is why the schema is
the first place a new task property is modelled.

## interlude: The core owns the record

The next four stops cross into the core package and the main process. The record
shape, the typed writer and the file envelope are one ownership boundary; the
process that holds the document is another. The renderer is not allowed to write
either one directly.

## apps/planner/packages/core/src/loro/WorkspaceDocument.ts#WorkspaceDocument

The typed facade is the only writer of a workspace. Every mutation validates
through Zod, sets the leaf keys that changed, and commits once. Opening a
snapshot assigns a fresh peer id and upgrades or refuses an older or newer
schema before any caller can read a record. A component that imported Loro
instead would be a second writer with none of those rules.

## apps/planner/packages/core/src/file/workspaceFile.ts#decodeWorkspaceFile

The file envelope is a small JSON object around an opaque base64 snapshot, and
decoding answers with a `Result` because the person chose the file. The refusals
are ordered and named: not JSON, not this format, a newer file version, a newer
schema, then a snapshot that will not decode. Decoding does not open a document
or merge anything; the caller decides what to do with the bytes.

### overlay: A newer file is not a damaged file

The version and schema refusals are terminal. Falling through to a backup and
then to a fresh workspace would leave an older build writing its schema over a
document it does not understand, so the store stops and tells the person which
version they need instead.

## apps/planner/src/main/workspaceStore.ts#WorkspaceStore

Main owns the authoritative document. A renderer edit arrives as an update and
is applied, then a debounced write assembles the envelope, copies the current
file to the backup, writes a temporary file and renames it into place. The flush
chain is serialised, so two saves cannot interleave, and a failed write is logged
without stopping every later save. The renderer never receives the path.

## apps/planner/src/main/ipc.ts#registerIpc

The whole capability set crosses one registration. `workspace:snapshot` hands
over the current document, `workspace:commit` accepts only a binary CRDT update,
and import and export own their native dialogs. Every handler refuses a sender
that is not the page this shell loaded, and every payload is parsed before it
reaches the store. The commit delta is also what sync publishes, so an edit does
not take a second path when a relay is on.

## interlude: The renderer owns the view

The path back is a snapshot and a projection. The renderer holds a replica, not
the authority; the day view is computed from records; and UI state such as the
selected date never becomes a second copy of the plan.

## apps/planner/src/renderer/src/store/snapshotStore.ts#DocumentReplica

This class is the renderer's single observe call site. A local edit is merged
into the replica, forwarded to main as a CRDT delta, and turned into a rebuilt
snapshot that React reads through `useSyncExternalStore`. An import or a synced
replacement detaches the old subscription and subscribes the new document, so a
stale observer cannot keep forwarding edits from a closed workspace.

## apps/planner/packages/core/src/plan/dayPlan.ts#dayPlan

A day is a projection over every task, not a stored list. The function decides
which tasks are scheduled for the date, which are overdue, which recurring
occurrences are due, and how much the planned work will take. Because it is pure
and rebuilds on every change, moving a task to another date needs no day record
to be edited in two places.

## apps/planner/packages/core/src/plan/capacity.ts#capacityFor

Capacity compares the same estimates against the day's available minutes and
returns a state rather than a colour. The ratio is derived, the empty day is
separate from a comfortable one, and an overfull day is a comparison rather than
a stored flag. A view that recomputed this itself would drift from the day plan
the moment one estimate changed.

## apps/planner/src/renderer/src/store/uiStore.ts#useUiStore

The Zustand store holds what the view is showing: the active surface, the
selected date, the selected task, the capture focus signal and the current
notice. It holds no task, no project and no snapshot. That boundary is what lets
the replica be replaced after an import without the UI losing its place, and it
is why a document edit never needs a store action.
