This tour follows one transaction through an envelope budget. The record is
validated, its amount is parsed into integer minor units, matching rules fill
the fields a person would otherwise type, the assignment and activity are folded
into an envelope, and every report is rebuilt from the same ledger. The core
package owns the record shapes, money, rules and projections; main owns the open
document and its file; the renderer owns the forms and the view state. Nothing
on the path opens a network connection, and there is no bank sync to opt into.

## apps/budget/packages/core/src/schema.ts#transactionSchema

A transaction is the only input the budget cannot derive: an account, a date and
a signed integer amount, with payee, category, memo, flag and cleared optional.
Zero is refused here, so no later projection has to defend against it. See the
Budget core module for the record set.

## apps/budget/packages/core/src/money.ts#parseMoney

Text becomes signed minor units in one place, rounded once at the currency
scale; a bad amount is a `Result`, and an amount that would lose digits is
refused. The Budget core module holds the parser and formatter.

### overlay: No float ever reaches the document

`parseFloat` and `toFixed` are banned outside the money file and its tests,
which is why the rest of the app can add amounts without its own rounding rule.
Formatting divides by the scale only at the display boundary; storage stays an
integer.

## apps/budget/src/renderer/src/accounts/TransactionDialog.tsx#TransactionDialog

The dialog owns the draft, not the record: it seeds from the snapshot, parses the
amount through `parseMoney`, and writes through the replica only on submit. A
reconciled row is locked, and a split parent updates its children as a set. The
Budget renderer module covers the form.

## interlude: The rule decides, the document records

The next three stops are the rule path. Rules are pure functions over a draft,
ranked so a specific rule wins over a broad one, and applied by the renderer
before a transaction is written or re-run over existing records.

## apps/budget/packages/core/src/rules/evaluate.ts#applyRules

Rules run in rank order over a copy of the draft: a condition reads one field,
an action replaces one, and the result carries the draft and the matched ids. An
invalid regular expression matches nothing, and the function never writes. The
Budget core module explains evaluation; the Budget rules module owns the order.

## apps/budget/packages/core/src/rules/rank.ts#rankRules

Disabled rules drop out first; the rest sort by stage, then ascending
specificity, then creation time and id. Broad rules therefore run before
specific ones, which gives the specific action the last word. The Budget rules
module explains why the order is total.

## interlude: The envelope is derived

An envelope is not a row that gets updated in place. Assigned amounts are
records, activity comes from transactions, and the available balance is a fold
over every month up to the one on screen. The document stores the inputs; the
core derives the envelope.

## apps/budget/packages/core/src/loro/BudgetDocument.ts#BudgetDocument

The typed document is the only writer. Record mutations parse with Zod and set
only the changed leaf keys, so concurrent edits merge; the outer call commits
once, and `batch` relies on that depth. A snapshot opens with a fresh peer id,
and undo travels as an ordinary delta. The Budget Loro module covers the
lifecycle.

## apps/budget/packages/core/src/plan/monthState.ts#monthState

The month state is the envelope fold: only a positive balance carries forward,
so an overspent envelope closes at the boundary instead of borrowing. Ready to
Assign is the on-budget balance minus what is already in envelopes. The Budget
core module covers the month fold.

## apps/budget/src/renderer/src/plan/PlanView.tsx#PlanView

The plan view renders the month state and sends actions back through the
replica. Auto-assign builds its delta map in core, the component applies it, and
the notice reports total and shortfall; collapsed groups, the prompt and the
month are view state. The Budget renderer module covers the view.

## apps/budget/packages/core/src/reports/budgetVsActual.ts#budgetVsActual

The report is a projection over month state, one row per category, so assigned,
activity and available are the plan's numbers and cannot drift. The Budget
reports module covers the report series.

## apps/budget/src/renderer/src/reports/ReportsView.tsx#ReportsView

Every tab rebuilds its figures from the current snapshot. The range and the
selected tab are React state; dashboard widgets are document records, but the
values inside them are computed on render. The page caption states the rule:
nothing is stored twice. The Budget renderer module covers the view.

## apps/budget/src/main/budgetStore.ts#BudgetStore

Main applies the renderer's delta, then debounces the write: back up the current
file, then replace it atomically. The flush chain survives a failure, `saveError`
reaches the renderer, and the renderer never writes the file. The Budget main
module covers the store.

## apps/budget/packages/core/src/file/budgetFile.ts#decodeBudgetFile

The `.budget` file is a JSON envelope around a base64 CRDT snapshot. Decoding
refuses in order: not JSON, not this format, a newer file version, a newer
schema, then a snapshot that will not decode. It returns bytes, not a document.
The Budget file module covers the envelope and the records export.
