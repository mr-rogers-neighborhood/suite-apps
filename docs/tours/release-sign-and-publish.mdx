A release is not just a build. It is a version with release notes, a commit the
gate has proven, and a signed OSTree summary for the Flatpak remote. This tour
follows the publishing path: what it refuses before building, what it signs, and
how a stable deployment and a pre-release branch keep separate identities. The
path is also the order to read a failed publish in, because each stop is a
refusal that happens earlier than the damage would.

The relay is a Flatpak on the same remote, so it has no second publishing path.
Its `sync-v<version>` tarball releases are retired history.

## scripts/release.mjs#versionFromPackage

The version has one home: the app's entry `package.json`. The script reads it and
never bumps it, so a tag cannot promise a version the tree does not name. Every
later check compares against this value.

## scripts/release.mjs#changelogProblem

A release note is what the tag promises, so the `## [version]` heading has to
exist before the tag. `Unreleased` is a section to write, not a version to
publish.

## scripts/release.mjs#gateProblems

The gate proof is a commit, not a working tree. The status file has to say the
run passed, came from a clean export, and names this commit. A warm checkout that
happens to pass is not evidence for the bytes about to publish.

## scripts/flatpak.mjs#run

The desktop path starts with `node scripts/flatpak.mjs`. It packages the unpacked
tree, exports the repository, signs the summary with the store key and installs
from the local remote. `--app sync` does the same for the relay.

## scripts/flatpak-remote.mjs#checkGitProof

Publishing the shared repository checks the same gate proof: a dirty tree or a
HEAD the status file does not name is refused before any byte is copied.

## scripts/flatpak-remote.mjs#verifySignedSummary

The fresh summary is verified in a throwaway Flatpak installation before it is
published. A repository that only looks signed is not enough.

## scripts/flatpak-remote.mjs#flatpakrepoText

The `.flatpakrepo` file embeds the store's public key. That is what lets a person
add the remote with `--from` and have Flatpak verify the summary from the first
fetch.

## interlude: One key, one writer

The Flatpak store key signs the OSTree summary, and it is the trust root for
every app on the remote, the relay included. The update key that signed the
retired relay tarball's `SHA256SUMS` has no artifact to sign; it and its pin are
kept until they are retired deliberately.

## scripts/lib/channel.mjs#flatpakId

Stable keeps `run.suite.<app>`; a pre-release takes `run.suite.slop.<app>`. That
id is the card and the profile, so stable and a pre-release can coexist without
sharing documents or an update path.

## scripts/lib/channel.mjs#branchFor

The tier is the Flatpak branch, not part of the id. One pre-release id across
`slop`, `canary` and `beta` means a tier move replaces the deployment instead of
adding a second install.
